## 一、红线与定位（先说清楚不做什么）

### 🔴 明确不做：洗稿

「洗稿」= 拿他人已发表文章做同义替换/段落重组/语序调换，以规避原创检测再发布。它同时踩三条线：

| 风险 | 说明 |
|---|---|
| 著作权 | 未经许可的改写再发布，触及改编权、署名权、信息网络传播权；「改词换序」不构成独创性表达，司法实践中通常仍认定侵权 |
| 平台违规 | 微信公众平台原创保护、知乎、掘金均有反洗稿机制；一经认定，轻则撤回原创标识、重则限流封号 |
| 商业与声誉 | 对做个人品牌/IP 的账号是致命伤，一次认定足以抵消长期积累 |

**因此：mopai 不提供、也不会提供「输入他人文章 → 输出改写稿」的任何功能路径。** CLI 不会新增 `rewrite`、`spin`、`洗稿` 之类的子命令；文档与代码中不把洗稿当作功能名出现。

### ✅ 明确定位：选题辅助 + 自有稿二次创作

服务对象只有一个：**用户自己拥有版权的内容**——自己的草稿、库存稿、已发布文章、笔记、演讲稿、内部文档。

在这个边界内，工具做的事是「把自己的一份内容，变成多种可用形态」，本质是**再分发**而非**再占有**：

- 一份自有长稿 → 公众号版 / 知乎版 / 掘金版 / 短帖版
- 一份自有稿 → 多个标题候选，挑一个发
- 一份自有稿 → 按标准骨架重排结构
- 一堆自有草稿 → 盘点出还能发的选题池

**边界声明（建议写进 README 与 CLI 帮助）**：
> 本工具的相关能力仅适用于您本人拥有完整著作权的内容。请勿将他人作品输入并要求改写。

## 二、功能清单（成本 / 依赖）

成本口径：低 = 1-2 天可交付；中 = 3-5 天；高 = 1-2 周且需持续维护。

| # | 功能 | 说明 | 成本 | 依赖 |
|---|---|---|---|---|
| F1 | **多版本改写（自有稿）** | 一份自有稿输出公众号/知乎/掘金/短帖 4 种形态：长度裁剪、语气切换、标题层级适配 | **低** | **零依赖**（v2.4 已落地 `toVariant` 的 zhihu/juejin，扩展短帖版与摘要版即可） |
| F2 | **标题多候选（规则法）** | 基于自有稿标题 + 正文关键词，套用固定句式生成候选：数字型、疑问型、对比型、结论型、痛点型 | **低** | **零依赖** |
| F3 | **标题/摘要质量体检** | 长度、关键词密度、是否有标题党特征、摘要是否 ≤120 字 | **低** | **零依赖**（v2.4 已有 `extractSummary` / `publishCheck`，直接扩展） |
| F4 | **结构重组** | 把自有稿段落按角色分类（观点/论据/数据/例子/结论），重排成「行途标准骨架」 | **中** | 零依赖规则法（段落特征匹配，准确率有限）；要更好需 **LLM** |
| F5 | **自有稿库盘点** | 扫描本地 drafts 目录，输出「未发布 / 已发布 / 可拆分 / 可合并」清单 + 选题池 | **低** | **零依赖** |
| F6 | **标题多候选（LLM 版）** | 同 F2，但由 LLM 基于全文语义生成，质量显著更高 | 中 | **需 LLM**（外部 API，破坏「零依赖 + 离线」卖点，须做成可选外部脚本，不进核心包） |
| F7 | **选题启发** | 基于自有稿库主题分布，指出「哪个方向写得多、哪个方向断更、哪篇可以拆成系列」 | 中 | 零依赖（统计法）／更好需 LLM |
| F8 | **热点/竞品选题雷达** | 抓取外部热点生成选题建议 | 高 | 需联网 + 数据源；**且合规风险高，建议不做** |
| F9 | **原创度检测** | 检测自有稿与已有内容的重合度 | 高 | 需语料库/联网；**且与洗稿场景强关联，不做** |

## 三、建议的首期落地项（挑 2 个）

选 **F1 + F2**，理由：成本最低、零依赖、不碰红线、能直接复用 v2.4 已有资产。

### F1 · 多版本改写（首期）

- 在 v2.4 的 `toVariant()` 基础上扩两个变体：
  - `weibo` / `short`：短帖版——保留标题 + 摘要 + 3-5 个要点，控制在 300 字内
  - `digest`：摘要版——标题 + 自动摘要 + 目录，用于合集/周报
- CLI：`--variant short` / `--variant digest`，输出 `.短帖版.md` / `.摘要版.md`
- 验收：同一份自有稿跑 4 个变体，产物均合法 Markdown，短帖版 ≤300 字，摘要版含自动摘要

### F2 · 标题多候选（规则法，首期）

- 输入：自有稿（取 H1 + 前 3 段 + 关键词）
- 输出：5-8 个候选标题，按句式模板生成，标注每个的类型
  - 数字型：`3 个方法，把 X 做成 Y`
  - 疑问型：`为什么你的 X 总是 Y？`
  - 对比型：`X 和 Y，差在哪一步`
  - 结论型：`结论：X 才是 Y 的关键`
  - 痛点型：`别再 X 了，试试 Y`
- CLI：`--titles`（只打印候选标题）
- 验收：候选数 ≥5，长度均在 15-30 字，无标题党夸张词（「3 分钟精通」这类进黑名单）

### 为什么不做 F6（LLM 版）作为首期

F6 质量更好，但会引入外部 API 依赖，与「零依赖、可离线、确定性输出」的核心卖点冲突。若要做，建议形态是**独立的可选脚本**（如 `tools/llm-titles.js`，用户自己配 key），不进 `package.json` 依赖、不影响核心引擎。

## 四、明确不做清单（写进文档，避免后续反复）

1. ❌ 输入他人文章 → 输出改写稿（洗稿）
2. ❌ 原创检测绕过 / 查重率降低
3. ❌ 热点抓取 + 洗稿式二次创作（F8）
4. ❌ 原创度检测（F9）
5. ❌ 任何需要联网才能跑通的核心功能

## 五、待拍板项

1. F1 的变体命名与产物后缀（`short`/`digest` 还是 `weibo`/`digest`）
2. F2 规则法标题候选：是否接受「模板套用」这种相对机械的质量（LLM 版质量高但破坏离线卖点）
3. 是否要把「仅适用于自有版权内容」的边界声明写进 README 合规章节 + CLI `--help`
4. F4 结构重组是否值得做（规则法准确率有限，容易生成错位的骨架，需先拿 2-3 篇自有稿实测）
